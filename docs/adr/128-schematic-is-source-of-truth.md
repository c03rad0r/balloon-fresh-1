# ADR 128: The Schematic Is The Source Of Truth — Board Derived From It, Mechanically Enforced

## Status

**Accepted** (2026-10-22). Operator directive.

Supersedes the *procedural* part of **ADR-028** (`schematic-first-three-variants`), which was
written 2026-08-05 for exactly this problem but left at status **Proposed** and therefore never
enforced. ADR-028's diagnosis and rule were right; this record makes the rule binding and
mechanical, and states the direction of derivation explicitly (ADR-028 did not say which file is
authoritative — its `check_sch_gates.py` says "the PCB netlist is the source of truth", which is
the **opposite** of this record).

2026-10-22

## Context — the measured state on 2026-10-22

The operator asked: *"Did you create a schematic before creating the board to be routed? I want
the board to be derived from a schematic at all times."*

The honest answer, measured:

| fact | evidence |
|---|---|
| **v9 HAS a schematic** | `schematics/flight_board/v9_flight.kicad_sch` (312 KB), generated by `build_flight_sch.py` (2743 lines) |
| **v10 has NO schematic** | no `*v10*.kicad_sch` exists; only `v10_flight.net` |
| **v10 was derived from a NETLIST TRANSFORM** | `make_v10_netlist.py --in v9_flight.net --out v10_flight.net` — a text transform of v9's netlist, not a schematic |
| **the direction is PCB → schematic** | `build_flight_sch.py` docstring: *"Derive a loading KiCad 9 schematic … FROM the frozen PCB"*; `check_sch_gates.py`: *"The PCB netlist is the source of truth; this script proves the schematic mirrors it"* |
| **ADR-028 already banned this** | ADR-028 §1: *"The previous workflow (Python script → .kicad_pcb → DRC → re-script) is banned"* — status **Proposed**, never Accepted, never enforced |
| **the v10 board is built by a Python builder** | `build_hub_board_v10.py` copies pads from footprints and assigns nets from the registry |

So the board the operator approved was **not derived from a schematic**, and the existing
schematic pipeline runs in the **wrong direction** — it renders a picture of the PCB rather than
defining it.

### Why this is a defect, not a documentation gap

The v10 stack added, by netlist text transform: a new module (`U_E28`), a new radio site (`U_C`),
a new bus split (ADR-123 two SPI buses), a programming header (`J_PROG`) and its reset RC. None
of that went through ERC. ADR-028 recorded the consequence of exactly that pattern on the
original board: *"527 DRC violations … shorts between SPI lines, power nets incompletely routed"*
and *"No schematic = no ERC = netlist errors propagate undetected into PCB layout."*

That risk is live on v10: `E28` pads 8/9 (`RX_EN`/`TX_EN`) are still unassigned, and `J_PROG`
pin 6 (`IO0`) dangles — both are *connectivity* questions that ERC exists to catch.

## Decision

### 1. The schematic is the source of truth; the board is derived from it

```
schematic (.kicad_sch)  →  ERC clean  →  netlist  →  board (.kicad_pcb)  →  DRC clean  →  fab
     ^ source of truth                                 ^ derived artefact
```

**No board file may be authored by a Python builder that invents connectivity.** A builder may
*place* components and *route* copper, but every net and every pin assignment must come from the
schematic. `build_hub_board_v10.py` currently assigns nets from `connectivity/v10_pinmap.reg`;
that is acceptable **only** as long as the registry is provably derived from the schematic (see
§3), otherwise it is a second, competing source of truth — which is the defect class ADR-028
named.

### 2. Direction of derivation is one-way and must be asserted

`build_flight_sch.py`'s PCB→schematic direction is **retired for connectivity**. It may keep
generating *symbol geometry and layout stubs*, but the connectivity it emits must be an INPUT it
receives, not a value it reads out of the board. The new gate (§3) fails if the schematic can be
regenerated from the board and differ.

### 3. Mechanical enforcement — `check_schematic_parity.py`

A convention is worth nothing the day someone forgets. This gate runs on every board commit and
fails on:

- **G1 SCHEMATIC EXISTS** — a board that is routed/ordered must have a `.kicad_sch` beside it.
  No schematic, no board.
- **G2 ERC** — `kicad-cli sch erc --exit-code-violations` on that schematic. An ERC error is a
  build failure.
- **G3 NET PARITY, BOTH WAYS** — every schematic net exists on the board and every board net
  exists in the schematic. A one-way check is not enough: a net added to the board by a script
  and absent from the schematic is exactly the v10 defect.
- **G4 NODE PARITY, BOTH WAYS** — per net, the `(ref, pin)` sets are equal.
- **G5 REGISTRY AGREEMENT** — `connectivity/v10_pinmap.reg` agrees with the schematic, so the
  builder's input cannot silently drift from the source of truth.
- **G6 REFUSAL** — if `kicad-cli` or the schematic is missing, the gate exits **non-zero with a
  REFUSED message**. A gate that cannot run must never look green.

### 4. Enforcement points

- **pre-commit hook** — runs when a `*.kicad_pcb` or `*.kicad_sch` is staged; a connectivity
  mismatch blocks the commit.
- **`route_escalating.sh`** — DRC and parity run **before any render is produced for the
  operator**, so a defect is fixed before it is shown.
- **AGENTS.md** — states the rule and the gate names, so a future session inherits it.

### 5. Known-open items this record does NOT close

Stated plainly so the record cannot be read as claiming more than it does:

- **v10 has no schematic yet.** This ADR makes that a *blocking* defect rather than an accepted
  state. The board is not fab-ready until §3 passes.
- The v9 schematic predates the v10 stack; it cannot simply be copied, because v10's changes
  (E28, U_C, SPI bus split, J_PROG) are exactly what must be *defined* in the schematic.
- `E28 RX_EN/TX_EN` and `J_PROG IO0` remain undecided; ERC will flag them, which is the point.

## Consequences

- **Positive:** connectivity errors are caught by ERC before copper exists, which is the class of
  error that produced the original 527-violation board. Pin assignment stops being a script
  secret and becomes a reviewed artefact.
- **Negative:** the v10 board must be re-derived from a new schematic before fab. That is real
  work — a symbol for `E28` and `U_C`, a sheet, and ERC-clean wiring — and it is work the project
  should have done before routing started. Sunk routing effort is not a reason to skip it.
- **Neutral:** placement and routing scripts survive; only their *authority over connectivity*
  is removed.

## For future sessions

- **The rule in one line:** the schematic defines connectivity; the board is derived from it;
  `check_schematic_parity.py` fails the build if they disagree in either direction.
- **Reproduce:**
  `python3 tracker/hardware/check_schematic_parity.py --board tracker/hardware/hub_board_v10.kicad_pcb --sch tracker/hardware/schematics/flight_board/v10_flight.kicad_sch`
- **Read first:** ADR-028 (the original diagnosis), then this record (the binding rule).
- **If the gate REFUSES** because the schematic is missing: that is the correct verdict on the
  current v10 state, not a bug in the gate.
